# Architecture Audit

**Source snapshot:** `bf329c0aa1a4e708f73085e5efe2dc30a346accd`

## Current architecture

The repository is a single Node.js/Express application with static frontend assets. The legacy dashboard API, research API, algorithms, data adapters, and experiment scripts coexist in one repository.

### High-level flow

```
Browser
  ├── Legacy dashboard ──> Express application API
  └── Research Lab ──────> Read-only research API
                              └── committed experiment artifacts

Express application
  ├── server.js
  ├── algorithms/
  ├── config/
  ├── data/
  └── routes/research.js

Research pipeline
  ├── experiments/
  ├── experiments/results/
  ├── research/
  └── test/
```

## Strengths to preserve

1. Research API is mounted separately from legacy endpoints.
2. Research endpoints read committed outputs and do not accept report submissions.
3. Research models are separated from the legacy dashboard's live risk calculation.
4. Algorithms are implemented as small CommonJS modules and can be unit-tested.
5. Research artifacts are generated by explicit scripts and stored in the repository.
6. The project has a CI workflow and a Node built-in test suite.
7. The deployment adapter is intentionally small.

## Architectural risks

### AR-01 — Server module has initialization side effects (High)
`server.js` creates the Express app, loads persistent data, potentially seeds synthetic data, and attempts a filesystem save at module import time. This couples app construction with runtime storage initialization.

**Recommendation:** Separate app construction from runtime initialization. Introduce an explicit initialization function or injected repository/storage adapter. Tests should construct the app without writing persistent runtime data.

### AR-02 — Persistence is process-local and file-backed (High)
A local JSON file is used for incident persistence. This may be acceptable for local prototyping but is not a durable multi-instance/serverless storage design.

**Recommendation:** Keep file persistence for local development if it meets current requirements. Define a storage interface before any future production datastore migration. Do not add a database until the target deployment and durability requirement justify it.

### AR-03 — Shared temporary filename (High)
The fixed temporary file name can collide across concurrent writes or processes.

**Recommendation:** Design and test a concurrency-safe persistence strategy. Include process-level and deployment-environment constraints in the design.

### AR-04 — Broad responsibilities in server.js (Medium)
The server file owns routes, input validation, rate limiting, data initialization, analytics, and response composition.

**Recommendation:** Extract only where a concrete testing or ownership benefit exists. A reasonable incremental target is routes/controllers, services, and storage adapters; avoid a wholesale rewrite.

### AR-05 — Research artifact parsing and API are coupled (Medium)
`routes/research.js` performs synchronous filesystem reads and contains CSV parsing logic inside the route module.

**Recommendation:** Consider a small artifact repository/service layer if it improves testability, caching, schema validation, or error handling. Preserve the read-only contract and avoid unnecessary abstraction.

### AR-06 — Serverless persistence boundary (High for production)
`api/index.js` exports the Express app, while runtime incident persistence is local-file based. The repository's README already notes that durable incident persistence requires an external store in serverless infrastructure.

**Recommendation:** Do not deploy the legacy write-enabled workflow as production-ready without a deliberate durable-storage and operational design. The Research Lab's static artifact/read-only path has a narrower operational surface.

## API boundary observations

The research router exposes:
- `GET /api/research/overview`
- `GET /api/research/models`
- `GET /api/research/allocation`
- `GET /api/research/routes`
- `GET /api/research/robustness`

Research endpoints read files from `experiments/results/` and return 503 when artifacts are unavailable. The test suite checks that a POST to the research overview endpoint is not accepted.

## Recommended architectural direction

1. Preserve the existing Node/Express and static frontend baseline.
2. Isolate application initialization from persistence.
3. Define a small persistence boundary for legacy incident reports.
4. Keep research artifacts read-only and versioned.
5. Keep research algorithms separate from dashboard heuristics.
6. Validate artifact schemas before presenting outputs.
7. Add browser-level verification before a major frontend redesign.
8. Treat serverless deployment as a distinct architecture decision, not a configuration-only step.

## Not recommended at this stage

- Framework migration.
- Microservices.
- Introducing a database without a confirmed production requirement.
- Replacing the Research Lab's static frontend solely for aesthetic reasons.
- Combining research scoring and legacy dashboard risk logic.
