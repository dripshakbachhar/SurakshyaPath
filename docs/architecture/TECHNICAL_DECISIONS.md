# SurakshyaPath — Technical Decision Record

**Phase:** 1 — Architecture and Development Baseline  
**Purpose:** Record evidence-based decisions and explicitly separate current facts from future proposals.

## Decision status vocabulary

- **Accepted:** decision is approved as the current project direction.
- **Proposed:** recommendation requiring implementation review or explicit approval.
- **Deferred:** decision is intentionally postponed until evidence or requirements exist.
- **Rejected:** considered and not selected.

## ADR-001 — Preserve the current modular-monolith stack

**Status:** ACCEPTED

### Context
The repository uses Node.js (>=18), Express 4, CommonJS modules, static HTML/CSS/JavaScript, and Node's built-in test runner. Existing research and API functionality is implemented in this stack.

### Decision
Continue with the existing stack for the current development cycle. Refactor incrementally within the repository.

### Consequences
- No React/Vue/Next.js migration is required for the Research Lab.
- No microservices split is justified.
- Existing tests and scripts remain the baseline.
- Any future framework/runtime change requires a concrete requirement, migration plan, and measured trade-off.

## ADR-002 — Research Lab is the primary product and remains read-only

**Status:** ACCEPTED

### Context
The Research Lab directly represents the manuscript's four-model study and committed experiments. The legacy dashboard contains report submission and operational-style risk/patrol/allocation interfaces that are outside the research product's intended promise.

### Decision
Keep the Research Lab as the primary product experience and preserve its read-only API boundary. Keep the legacy dashboard separate and out of the Research Lab user journey.

### Consequences
- No incident submission, public report storage, geolocation, dispatch, staffing advice, or live patrol recommendation is added to the Research Lab.
- Research endpoints remain GET-only.
- The legacy UI can remain available as an isolated prototype while its future status is reviewed.
- Product copy must state synthetic-data and non-operational boundaries.

## ADR-003 — Keep research models separate from legacy heuristics

**Status:** ACCEPTED

### Context
The research suite compares frequency-only, severity-only, frequency × severity, and severity × recency models. Legacy risk/intelligence code uses different inputs and severity assumptions.

### Decision
Maintain distinct modules, configuration, names, API contracts, tests, and UI explanations for research models and legacy dashboard heuristics.

### Consequences
- Do not consolidate formulas solely to reduce duplicate-looking code.
- Shared utilities are allowed only when their semantics are genuinely identical and regression-tested.
- Legacy endpoints must not become the source of Research Lab results.

## ADR-004 — Treat all canonical spatial records as synthetic

**Status:** ACCEPTED

### Context
The canonical dataset contains 1,567 deterministic synthetic records. Aggregate official statistics are contextual reference material, not official geocoded incident-level observations.

### Decision
Disclose synthetic status in data, API, UI, figures, documentation, and exported artifacts. Do not describe these records as actual police incident reports.

### Consequences
- No predictive accuracy, causal impact, fairness, or real-world effectiveness claim is supported by the current dataset.
- Five deterministic seeds are designed scenarios, not independent samples.
- Normalized model scores are not probabilities.

## ADR-005 — Do not infer event-hour precision from age_days

**Status:** ACCEPTED

### Context
The canonical CSV stores `age_days`, not a timestamp with event-hour and timezone precision. The current runtime adapter derives a timestamp by subtracting age days from the current snapshot clock. Downstream local-hour calculations therefore inherit an arbitrary clock hour.

### Decision
Age-only records must not generate observed hour-of-day, peak-hour, night-share, or evidence-based allocation-window claims. Represent temporal precision as unavailable unless a future data source provides valid event timestamps and a documented timezone policy.

### Consequences
- Phase 2 prioritizes removal/suppression of unsupported derived metrics.
- Tests must distinguish age-only synthetic records from records with genuine timestamps.
- Timezone conversion alone is not an acceptable fix.
- Research formulas and committed artifacts must not be altered as a shortcut.

## ADR-006 — Keep committed research artifacts as the Research API source of truth

**Status:** ACCEPTED

### Context
The current Research API reads committed JSON/CSV outputs generated by deterministic scripts. This makes the displayed study inspectable and version-controlled.

### Decision
Retain version-controlled research artifacts as the API source for the current Research Lab. Add schema/provenance validation before expanding artifact formats.

### Consequences
- No runtime database is required for research results.
- API responses should not recompute undocumented values on every request.
- Artifact changes require reviewed generation diffs and reproducibility checks.
- A future dynamic experiment runner would be a separate feature with resource and abuse controls.

## ADR-007 — Introduce a validated artifact boundary

**Status:** PROPOSED

### Context
The research router currently reads files and parses JSON/CSV directly. Formal schema validation is not demonstrated, and the CSV parser assumes simple comma-separated fields.

### Proposal
Create a small artifact access/validation boundary if it materially improves tests and failure behavior. Validate schema versions, model IDs, zone counts, numeric fields, allocation conservation, route membership, and seed/result consistency.

### Consequences if accepted
- Invalid artifacts fail closed.
- API handlers remain focused on HTTP composition.
- Error responses remain stable and do not leak file paths.
- CSV parser behavior becomes explicit and tested.

**Approval gate:** Phase 4 implementation review.

## ADR-008 — Separate Express app construction from runtime initialization

**Status:** PROPOSED

### Context
Importing `server.js` currently loads/seeds incident state and attempts a persistence write. The Vercel adapter imports this module. This couples app construction to local filesystem state.

### Proposal
Move app creation and route composition into a side-effect-free module. Put storage loading/seeding and runtime startup in an explicit initialization boundary. Allow tests to create an app with injected dependencies or isolated fixtures.

### Consequences if accepted
- Importing the app does not write files.
- Tests become isolated from repository runtime data.
- Local startup remains explicit and predictable.
- Existing public exports may need compatibility wrappers.

**Approval gate:** Phase 3 implementation review.

## ADR-009 — Keep local JSON persistence as a development adapter only

**Status:** PROPOSED

### Context
Legacy incident persistence currently writes `data/incidents.json` using a fixed temporary path. This is process-local and unsuitable as shared durable storage for multi-instance/serverless deployment.

### Proposal
Retain a file-backed adapter only for local development if needed. Define a persistence interface and test its guarantees. Do not select or provision a production database until requirements and hosting target are approved.

### Consequences if accepted
- No database migration is introduced in the architecture phase.
- Concurrency and atomic-write behavior must be tested for the supported local environment.
- Serverless deployment cannot claim durable write support until a durable shared adapter is selected.

**Approval gate:** Phase 3 for interface/local adapter; Phase 8 for production storage choice.

## ADR-010 — Preserve geometric routing labels and limitations

**Status:** ACCEPTED

### Context
The route experiment uses great-circle/haversine distance and compares route-order algorithms. It does not use a validated road network or traffic source.

### Decision
Label distances as geometric/great-circle distances. Do not display the legacy estimated travel time as a research result. Do not imply turn-by-turn guidance or operational route suitability.

### Consequences
- Route API and charts carry units and method context.
- No routing provider integration is added in the MVP.
- Any future road-network experiment requires a new method, data source, cost review, and separate results.

## ADR-011 — Defer database, authentication, and multi-tenant infrastructure

**Status:** DEFERRED

### Context
The intended Research Lab is read-only and uses committed public synthetic artifacts. No account, user-specific data, or multi-tenant requirement has been established.

### Decision
Do not add a database, authentication provider, or multi-tenant system during the current research-first rebuild unless a specific requirement emerges.

### Revisit when
A durable public write workflow, user accounts, private data, or a production operational service is explicitly approved.

## ADR-012 — Require evidence-based release gates

**Status:** ACCEPTED

### Context
Static inspection, local tests, GitHub Actions, browser verification, accessibility, security, and deployment each provide different evidence. One does not prove the others.

### Decision
Each phase reports only checks actually run and results actually observed. Production deployment and merge require explicit user approval.

### Consequences
- Phase status uses PASS, PASS WITH DOCUMENTED LIMITATIONS, or BLOCKED.
- No unsupported claims about test success or production readiness.
- Preview and production deployment remain separate gates.
- No force push, automatic merge, or automatic production promotion.

## Decision review policy

Revisit a decision only when:
- a requirement changes;
- new evidence contradicts the recorded assumption;
- a test demonstrates a defect;
- a security or deployment constraint changes;
- a proposed decision is approved for implementation.

When revising a decision, record the date, reason, alternatives, consequences, and migration implications. Do not silently rewrite the research method or architecture history.
